# Auto Skill 功能说明与业务选项

> 面向产品与业务方的功能说明。技术契约见 [backend/docs/AUTO_SKILL.md](../backend/docs/AUTO_SKILL.md)。
>
> 一句话定义：**平台在一次问答完成后，自动把这次「怎么取数、怎么推理、怎么成稿」沉淀成一个可复用技能，下次同类问题直接被匹配并照做。**

---

## 1. 功能价值

| 解决的问题 | 带来的收益 |
|---|---|
| 同一类问题每次都要重新摸索"调哪些 MCP 工具、传什么参数、按什么顺序" | 首次答对后固化成路径，后续直接复用 |
| 同类问题的回答结构因人、因时而异 | 技能里固定回答模板，产出稳定可预期 |
| 业务专家的取数口径只存在人脑里 | 从真实运行轨迹提炼成可审阅的 `SKILL.md` |
| 人工编写技能门槛高、成本高 | 零人工，运行完自动产出，且安全等级与手写技能一致 |
| 新人不知道该问什么、怎么问 | 技能描述里的触发词本身就是"该场景怎么描述"的提示 |

与内置的 `skill_evolution`（Agent 运行中主动调 `skill_manage` 写技能）互补：

| | `skill_evolution` | `auto_skill` |
|---|---|---|
| 谁来写 | Agent 自己决定 | 平台在回答交付后自动执行 |
| 回合成本 | 消耗一个 Agent 回合 | 零回合，不打扰对话 |
| 视角 | 只看 Agent 主动记录的内容 | 看完整轨迹（含每个工具的真实返回） |
| 结果范围 | 写者本人的 custom 技能 | **全局，所有用户** |

## 2. 完整流程

```
用户提问
  └─ 正常链路：技能匹配 → 推理取数（MCP）→ 生成回答 → 流式交付
       （auto-skill 在此时不参与任何决策，不影响延迟与结果）

run 完成（回答已送达）
  └─ AutoSkillMiddleware.after_agent          仅 lead 链
       ├─ 轨迹提取：提问 / 工具步骤 / 命中技能 / 计划 / 最终答案（全字段限长）
       ├─ 门禁过滤：开关 / 有提问 / 有答案 / 成功工具调用数
       └─ 入队（O(1)，立即返回）

防抖窗口到期（默认 20s）
  └─ 后台线程逐条合成
       ├─ 若本次命中了已有自动技能 → 把该技能全文交给模型对比
       ├─ 模型返回 decision：create / update / no_change
       ├─ no_change → 结束，一个字都不写
       ├─ create/update → 渲染 SKILL.md
       ├─ 四道安全门（名称校验 / frontmatter 解析 / 确定性扫描 / LLM 审核）
       ├─ 全局发布（跨进程锁 + 暂存 + 原子替换，旧版进备份库）
       ├─ 全局缓存失效（所有用户、所有 worker）
       └─ 版本保留清理 + 旧版按用户技能迁移

下次同类提问
  └─ 技能列表刷新 → 描述命中 → 模型读取 SKILL.md → 按其中路径执行
```

## 3. 业务选项与设计选择

> 说明：**「当前选择」是已实现并生效的**；「可选方案」中标注了哪些改配置即可、哪些需要改代码。

### 3.1 可见范围（谁能用）

| | 说明 |
|---|---|
| **当前选择** | **全部用户**：写入 `{DEER_FLOW_HOME}/integrations/skills/auto-skill/`，每个用户都能匹配到，且默认启用 |
| 可选方案 | ① 单用户（只写者本人可用）② 指定角色/用户组 ③ 全局 + 白名单可见 |
| 为什么选全部用户 | 业务知识的价值不在于"谁问出来的"；A 摸索出的路径让 B 直接受益，平台能力随使用累积而非各自重复建设。同时该目录是唯一"每用户都无条件扫描 + 运行时可写 + 默认启用"的位置 |
| 代价 | 一个人的运行会塑造所有人的 Agent；靠安全门 + `no_change` 纪律 + `min_tool_calls` 控制质量，靠备份库 + 回滚兜底 |
| 如何切换 | 需改代码：`store.py::auto_skill_root()` 的落点。单用户方案应改为 `paths.user_custom_skills_dir(user_id)` |

### 3.2 生成条件（什么情况才学）

| | 说明 |
|---|---|
| **当前选择** | **不限制业务领域**，只用四条技术门禁：功能开关开、有真实用户提问、有可见最终答案、**成功工具调用数 ≥ `min_tool_calls`（默认 1）** |
| 可选方案 | ① 仅企业/产业相关问题 ② 仅命中过 MCP 数据服务 ③ 仅多步复杂任务（如工具调用 ≥ 3）④ 仅计划模式 ⑤ 仅高价值问题（人工标记/评分） |
| 当前实际上被收窄到什么程度 | 平台已关闭全部公网工具（`web_search`/`web_fetch`/`image_search`）且 `bash` 被 `allow_host_bash: false` 门控，因此**任何带工具调用的运行只能来自内网 MCP**。但注意：纯文件工具（`write_file`/`read_file`）也能满足 `min_tool_calls=1`，所以"必然是 MCP"并非强约束 |
| 如何切换 | ①③④ 部分可用现有配置近似：调高 `min_tool_calls` 即可过滤浅层运行；「仅计划模式」需改代码。② 需要新增一个门禁：**要求至少一次成功调用来自 MCP 工具**（推荐，实现点在 `auto_skill_middleware.py::_is_worth_learning`，用工具的 `deerflow_mcp` 元数据判断） |

> **建议**：如果业务上只关心"企业/产业相关问题"，最省事的落地是加上 ②（至少一次 MCP 调用）。比按关键词判断领域更稳——工具来源本身就是最可靠的领域信号。

### 3.3 用户可见性（是否出现在用户的技能列表里）

| | 说明 |
|---|---|
| **当前选择** | **用户可见**：出现在"设置 → 技能"列表中，类别为 `integrations`，标记 `editable=false` |
| 可选方案 | ① 完全隐藏（后台资产，仅 Agent 内部可用）② 可见但折叠在"系统自动生成"分组 ③ 仅管理员可见 |
| 为什么选可见 | 透明可审计——用户能看到 Agent 学到了什么、口径对不对；出问题时能识别来源 |
| 代价 | 列表会随时间变长（当前 10 个全局技能 + 每个场景 1 个） |
| 如何切换 | 完全隐藏需改代码（在 `skills.py` 列表接口过滤 `integrations/auto-skill` 前缀）。若只想让**某个用户**看不到某个技能，可在该用户的 `_skill_states.json` 里设 `enabled: false`（存储层支持按用户隔离启用状态，但目前 UI 未暴露该入口） |

### 3.4 可编辑性（用户能否修改）

| | 说明 |
|---|---|
| **当前选择** | **不可编辑**：`integrations` 类别对普通用户只读（`editable=false`），与飞书官方技能包同级 |
| 可选方案 | ① 允许用户直接改（风险：一人改坏全员共享）② 允许管理员改 ③ 只读 + 同名遮蔽（当前） |
| 为什么选只读 | 全局资产不允许单点破坏。默认生成内容已经过四道安全门，但不等于业务上一定正确 |
| 用户个性化路径 | **同名遮蔽**：用户自建一个同名 custom 技能即可覆盖全局版，只影响自己。这是平台既有机制（CUSTOM 在 INTEGRATION 之后扫描，同名后者胜出） |
| 管理员修改路径 | 直接改磁盘文件：`{DEER_FLOW_HOME}/integrations/skills/auto-skill/{name}/SKILL.md`（`load_skills()` 每次调用都重扫，改完即生效） |

### 3.5 版本呈现（更新后旧版还能看到吗）

| | 说明 |
|---|---|
| **当前选择** | **只看最新版**：技能名稳定为 `{prefix}-{场景slug}`，不含版本号；版本只存在 `metadata.version` 和备份目录名里 |
| 可选方案 | ① 保留所有版本并列可见（`v1`/`v2`/`v3`…）② 只看最新（当前）③ 保留最近 N 个可见 |
| 为什么选只看最新 | 「用户只能看到最新版本」是**结构性保证**而非清理结果——每个场景恒只有一个可见包。且更新不改名，`skill_context` 引用、书签、外部引用都不会失效 |
| 旧版去哪了 | `{DEER_FLOW_HOME}/auto-skill-backup/{场景名}/v{n}/SKILL.md`，可随时 `restore_backup()` 回滚（回滚本身也是一次版本递增，可撤销撤销） |
| 保留多少个 | `max_versions`（默认 5），超出自动清理最旧的 |

### 3.6 生成触发策略（每轮都学，还是判定后再学）

| | 说明 |
|---|---|
| **当前选择** | **每轮候选 + 模型判定**：每轮都进入候选，但若本次命中了已有技能，模型必须显式判定 `no_change` / `update` / `create` |
| 可选方案 | ① 每轮无脑新建 ② 仅人工触发 ③ 仅在命中已有技能时判定（当前）④ 仅在失败/纠正后重学时学 |
| 为什么这样 | `no_change` 在安全扫描**之前**短路——只是"同一路径换了具体数值"的运行成本仅为一次模型调用，不会产生版本噪音，也不做无谓扫描 |
| 实际效果 | 实测同一问题第二次运行时，模型判定 `no_change` 并给出理由：「已有技能完整覆盖了取数路径、字段口径处理与回答格式……本次只是同一路径下的具体取值不同」 |

### 3.7 安全门槛（生成内容怎么把关）

| | 说明 |
|---|---|
| **当前选择** | **四道门全开**：① 技能名合法性 ② frontmatter 可解析且 `name` 一致 ③ 确定性扫描（SkillScan，CRITICAL 直接拦）④ LLM 内容审核（`block` 则一字不落盘） |
| 可选方案 | ① 只留确定性扫描（快、便宜、看得住代码注入，不懂语义）② 只留 LLM 审核（懂语义但可被绕过、有成本）③ 两者都留（当前）④ 再加人工审批队列 |
| 如何切换 | ③ 是默认。`skill_scan.enabled: false` 可关掉确定性扫描的可配置部分（归档安全检查仍强制）；`skill_evolution.security_fail_closed` 控制审核模型不可用时的策略（当前 `true`，即宁可拒绝） |
| 额外防伪造 | 渲染层剥离模型文本首行的标题（避免与模板标题重复）、剥离前导 `---`（防止伪造第二段 frontmatter）、所有 frontmatter 标量走 JSON 转义 |

### 3.8 备份保留策略

| | 说明 |
|---|---|
| **当前选择** | 每场景保留最近 `max_versions`（默认 **5**）个历史版本，超出删除最旧的 |
| 可选方案 | ① 不保留（省钱省空间，但无法回滚）② 保留 N 个（当前）③ 永久保留 ④ 保留全部但转冷存储 |
| 为什么选 5 | 单版本约 3–5 KB；5 个足以覆盖"改坏了要退回上一版"的常见诉求，同时避免无限增长 |
| 如何切换 | `max_versions` 配置项；设为 1 即"只留上一版"，设大即延长历史 |

### 3.9 合成模型选择

| | 说明 |
|---|---|
| **当前选择** | `model_name: null` → 用默认对话模型（当前部署为 `deepseek-v4.1-flash`，`models[0]`） |
| 可选方案 | ① 用默认模型（当前）② 指定一个更便宜/更快的模型专门做沉淀 ③ 指定一个更强的模型保证技能质量 |
| 取舍 | 合成是后台任务，质量比速度更重要；但若频率高，用便宜模型更划算。合成结果还有 LLM 审核兜底，所以用快模型的风险可控 |
| 如何切换 | `auto_skill.model_name: <模型名>`（热重载） |

### 3.10 性能与成本取舍

| 维度 | 当前选择 | 说明 |
|---|---|---|
| 对用户延迟的影响 | **零** | 钩子只做内存提取 + 入队，模型调用与写盘全在后台 |
| 批量合并 | 防抖 20s（当前部署调成 10s） | 窗口内多轮合并为一批，只按首次提交计时，不会被持续流量饿死 |
| 单次成本 | 1 次合成调用 +（非 `no_change` 时的）1 次审核扫描 | `no_change` 跳过扫描 |
| 队列上限 | 64，满了拒新不淘汰旧 | 已入队的都是已付出算力的真实经验 |
| 崩溃丢失 | 待处理条目会丢 | 与记忆队列同一取舍；优雅关停会排空（上限 30s） |

## 4. 配置项一览

```yaml
auto_skill:
  enabled: true                  # 总开关（默认 false，因为会写盘）
  model_name: null               # null = 默认对话模型
  name_prefix: "auto"            # 可见名前缀，hyphen-case，≤32 字符
  min_tool_calls: 1              # 成功工具调用数低于此值不学
  max_trajectory_chars: 24000    # 交给合成模型的轨迹总预算
  max_tool_result_chars: 2000    # 单条工具返回预算
  debounce_seconds: 20           # 防抖窗口（当前部署 10）
  max_versions: 5                # 每场景备份保留数
  queue_max_size: 64             # 待处理上限
  shutdown_flush_timeout_seconds: 30  # 优雅关停排空上限
```

`auto_skill` 是**热重载**字段：改完下一轮 Agent 装配即生效，无需重启。`.env` 变更例外——`env_file` 只在容器创建时读取，必须 `--force-recreate`。

## 6. 运维操作

| 需求 | 操作 |
|---|---|
| 查看有哪些自动技能 | `GET /api/skills`（列表）或看磁盘目录 |
| 看某个技能的完整内容 | `GET /api/skills/{name}`，或直接读 `SKILL.md` |
| 临时停用所有自动沉淀 | `auto_skill.enabled: false`（热重载） |
| 手工修正某个技能 | 直接改 `SKILL.md`（改完即生效，不需要重启） |
| 回滚到上一版 | `store.restore_backup(name, version)`（回滚也是一次版本递增） |
| 彻底删除某个技能 | 删除对应目录，并重启或等下一轮 Agent 装配 |
| 把旧版按用户技能并入全局 | `store.migrate_legacy_user_skills(user_id)` |
| 查看学习过程 | Gateway 日志里搜 `auto-skill`（记录 `create`/`update`/`no_change` 与判定理由） |

## 7. 已知边界

1. **合成失败是静默的**（只记日志）。这是刻意设计——学习是纯增益，绝不能影响已交付的回答。
2. **`no_change` 依赖模型判断**，模型可能误判"需要更新"而产生冗余版本。`max_versions` 与备份回滚是兜底。
3. **技能名由模型起、代码归一化**。纯中文场景名会退化为 `q<哈希>`，可匹配但可读性差。
4. **领域过滤尚未实现**。当前靠"公网工具关闭"间接约束，但纯文件操作类运行仍会产生技能。若需要严格"仅企业产业相关"，建议增加"至少一次 MCP 调用"门禁。
5. **跨用户共享是双刃剑**：一次错误的运行会影响所有人。缓解手段是四道安全门、`no_change` 纪律、备份回滚，以及同名 custom 技能遮蔽。
